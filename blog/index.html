1. Introduction

Building, testing and deploying by hand works for a weekend project. On a team it breaks down: someone forgets to run the tests, a build works on one laptop and fails on another, and a release becomes a stressful checklist.

Git tracks your code, GitHub hosts and organizes it, GitHub Actions runs automated tasks when something happens in the repository, and CI/CD is the practice those tasks implement. By the end you will understand each piece and have working CI workflows for an Angular app and an ASP.NET Core Web API.

2. What is Git?

Git is a distributed version control system. Every developer has a full copy of the project history, so you can track changes, work on branches in isolation, save snapshots called commits, collaborate by merging work, and revert when something goes wrong.

Bash
git init                      # start a repository
git clone <url>               # copy an existing repository
git status                    # see what changed
git add .                     # stage all changes
git commit -m "Initial commit"
git push                      # upload commits to GitHub
git pull                      # download and merge remote changes
git branch                    # list or create branches
git merge <branch>            # merge a branch into the current one

Workflow: initialize and push to GitHub

Create an empty repository on GitHub first, then run:

Bash
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/your-username/your-repo.git
git push -u origin main

3. What is GitHub?

GitHub is a cloud platform for hosting Git repositories and collaborating on them. Key concepts: a repository holds your code and history; branches and commits work as in Git; a pull request proposes merging a branch; issues track tasks and bugs; code review lets teammates comment before merging.

Bash
my-app/
├── src/
├── package.json
├── README.md
└── .github/
    └── workflows/        # GitHub Actions workflows live here

# Typical branch workflow
git switch -c feature/login
git add . && git commit -m "Add login form"
git push -u origin feature/login   # then open a pull request

4. What is CI/CD?

  • Continuous Integration (CI): merge small changes often; every change is built and tested automatically so errors surface early.
  • Continuous Delivery: every successful change is packaged and ready to release. Production deployment may need a manual approval.
  • Continuous Deployment: successful changes go to production automatically, with no routine manual approval.

6. Create Your First GitHub Actions Workflow

Create .github/workflows/angular-ci.yml in your Angular repository:

YAML
name: Angular CI Pipeline

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  build:
    name: Build Angular Application
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v6

      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '20'

      - name: Install Dependencies
        run: npm ci

      - name: Build Angular Application
        run: npm run build
  • name: label shown in the Actions tab.
  • on: events that start it, here pushes and pull requests targeting main.
  • jobs.build: one job; runs-on: ubuntu-latest picks a GitHub-hosted Linux runner.
  • actions/checkout: downloads your repository onto the runner.
  • actions/setup-node: installs the Node.js version in node-version.
  • npm ci: clean, reproducible install from package-lock.json.
  • npm run build: runs the build script from package.json; a failure fails the workflow.
Important: the Node.js version must be compatible with the Angular version your project uses. Check the Angular version compatibility table, then change node-version to match.

Steps

  1. Create the directory: mkdir -p .github/workflows
  2. Create angular-ci.yml inside it.
  3. Paste the configuration above.
  4. Commit and push: git add . && git commit -m "Add Angular CI" && git push
  5. Open your repository on GitHub and click the Actions tab.
  6. Select the latest run of "Angular CI Pipeline" and open the build job.
  7. Read the result: a green check means every step passed. A red cross means a step failed; expand it to read the log, fix the cause, and push again.

7. ASP.NET Core CI Pipeline

Create .github/workflows/dotnet-ci.yml in your Web API repository:

YAML
name: ASP.NET Core CI Pipeline

on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v6

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.0.x'

      - name: Restore Dependencies
        run: dotnet restore

      - name: Build Application
        run: dotnet build --no-restore

      - name: Run Tests
        run: dotnet test --no-build

The steps: check out the repository; install the .NET SDK; restore NuGet packages; build the solution (--no-restore reuses the restored packages); run automated tests (--no-build reuses the build).

Note: this example assumes a .NET 10 solution with test projects. Adjust the SDK version and working directory (working-directory:) to match your project.

8. Understanding CI/CD Deployment

A full pipeline runs: code push, automated build, automated tests, package generation, deployment, and production verification (a smoke test or health check).

Typical targets include Azure, AWS, a VPS, or private hosting servers. Whatever you choose, never hardcode passwords, tokens or keys in the repository. Store them as GitHub Secrets and read them in the workflow:

YAML
- name: Deploy Application
  run: echo "Deployment started"
  env:
    DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

Add a secret via GitHub Repository → Settings → Secrets and variables → Actions, then choose New repository secret. GitHub masks secret values in logs.

9. Important GitHub Actions Features

Triggers, manual runs and schedules

YAML
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:        # adds a "Run workflow" button
  schedule:
    - cron: '0 2 * * *'     # daily at 02:00 UTC

Multiple jobs and dependencies

YAML
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "build"
  deploy:
    needs: build            # runs only if build succeeds
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploy"

Artifacts

YAML
- name: Upload build output
  uses: actions/upload-artifact@v4
  with:
    name: angular-dist
    path: dist/

The GitHub Actions Marketplace offers thousands of reusable actions. Check the version tags shown in each action's own README before pinning one.

10. Benefits of GitHub Actions and CI/CD

  • Saves time: no repeated manual builds and checks.
  • Early error detection: broken changes fail on the pull request, not in production.
  • Consistent builds: every run starts from a clean machine.
  • Better collaboration: reviewers see pass/fail status on every pull request.
  • Reliable deployments: the same scripted process every time.
  • Improved quality: tests run on every change.

11. Common Mistakes Beginners Should Avoid

MistakeSolution
Incorrect Node.js or .NET versionMatch the version to your Angular or .NET project.
Missing package-lock.jsonCommit it; npm ci requires it.
Incorrect workflow directoryFiles must be in .github/workflows/ and end in .yml or .yaml.
Incorrect build commandsConfirm the script exists in package.json, or the .NET solution path is right.
Exposing credentialsUse GitHub Secrets; rotate anything that was committed.
Missing automated testsAdd at least basic tests so CI means something.
Ignoring failed workflow logsOpen the failed step and read the error first.
Using untrusted third-party actionsPrefer official or well-reviewed actions and pin versions.

12. Conclusion

Git records your history, GitHub hosts and reviews it, GitHub Actions runs automation on it, and CI/CD is the habit of building, testing and delivering every change automatically. Start small: add a build-only workflow, then automated tests, then deployment.

The goal of automation isn't just to write less code manually. It's to build, test, and deliver better software more consistently.
